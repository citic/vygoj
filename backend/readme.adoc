= Vygoj Backend

The Vygoj Backend is a Code Execution Service because provides a web service to allow web applications to run source code into a sandboxed environment. It supports tests for concurrent programming. Distributed programming may be supported in the future. The following steps run it on a Debian-based distribution:

[source,bash]
----
# Install Docker and create a Debian image
$ cd engine
$ sudo make install  # If Docker is not already installed
$ make image
$ cd ..

# Install dependencies and run the backend. Requires Python 3
$ sudo apt install python3
$ make release
----



[user_manual]
== User manual

NOTE: A running Docker server is needed before running the backend. Read link:engine/readme.adoc[VygOJ Engine's documentation] to install and run the Docker server before continuing.

The backend is developed in Python and requires Flask. A `Makefile` is provided to ease this process on Debian-based distributions. The default rule creates a Python virtual environment, installs dependencies, and run the backend for debugging:

[source,bash]
----
$ make
----

In production server, you can run the backend with no debug reporting:

[source,bash]
----
$ make release
----

For keeping the backend server running in background even after logging out from the terminal, you can use `gunicorn`:

[source,bash]
----
$ make server
----

The server writes its logs (`access.log`, `error.log`) and its process id (`gunicorn.pid`) in the `data/` folder, which is ignored by Git. Stop the server with `make stop`.

You can remove the virtual environment when it is no longer needed:

[source,bash]
----
$ make clean
----

[[languages]]
== Programming languages

The backend runs solutions in C, C++, Java, and Python (`LANGUAGE_DEFAULTS` in `src/execution.py`). Each language has a fixed source file name, its compiler command and compile time limit, and the command that runs the solution. Python is interpreted, so its "compiler" only checks the syntax, and students get their syntax errors as compiler errors before any test case runs:

[cols="1,2,3,1,2"]
|===
| Language | Source file | Compiler | Compile limit | Run

| C | `solution.c` | `gcc -g -Wall -Wextra -std=gnu17 -pthread` | 2 s | `./solution`
| C++ | `solution.cpp` | `g++ -g -Wall -Wextra -std=gnu++20 -pthread` | 2 s | `./solution`
| Java | `Solution.java` | `javac -g -encoding UTF-8 -Xlint:all -d .` (the default JDK of Debian trixie) | 10 s | `java -ea -cp . Solution`
| Python | `solution.py` | `python3 -m py_compile` (Python 3 of Debian trixie) | 2 s | `python3 solution.py`
|===

Java requires a public class to be in a file of its name, so the main class of a Java solution must be the public class `Solution`, as in the default code of the frontend. Java solutions run with assertions enabled (`-ea`). The sanitizers (`asan`, `tsan`, `ubsan`) and valgrind (`memcheck`, `helgrind`) work only on native executables, so they are ignored for Java and Python, as is `lint`, which runs `cpplint` on C and C++ only. `gdb` counts the threads of C, C++, and Python solutions (the threads of Python are threads of the operating system), but not of Java, whose virtual machine creates threads of its own.


The backend runs code written by untrusted users, so each submission runs in a disposable container created with restrictions (see `_create_container()` in `src/execution.py`):

* Unprivileged `student` user, all Linux capabilities dropped, `no-new-privileges`, and the default seccomp profile of Docker. The container never runs in privileged mode.
* No network.
* Limits of memory (512 MiB without swap), processes and threads (512), CPUs (2), file size (64 MiB), open files (4096), and a 64 MiB `/tmp` kept in memory.
* Every command has a time limit, its output is truncated to 1 MiB per stream, and student processes left in background are killed after each test case. The whole submission is killed after 100 seconds.
* Command line arguments of test cases are split as a shell would, but they are never interpreted by a shell.

`/run` answers an `ExecutionResult` in compact JSON. Each test case reports its wall time, its CPU time (all threads added up), its maximum memory, measured with `/usr/bin/time -v`, and, when the problem asks for a minimum of threads, the secondary threads it created, counted with `gdb` in another run with the same arguments and input. The time limits and the thread counts are checked for each test case on its own. Outputs are compared complete, but the answer carries only the first `maxOutputSize` bytes of the problem (at most 1 MiB) of the standard output and error of each visible test case, and of the compiler output, followed by `(truncated)`. Hidden test cases carry no output.

The frontend sends the effective limits in the problem; the backend only clamps them to its own ranges (`MAX_DURATION`, 30 seconds per test case, and `MAX_TOTAL_DURATION`, 120 seconds per submission, in `src/execution.py`), which must contain the ranges of its frontends. Each test case runs at most its `maxDuration` (2 seconds if missing), enforced by `timeout` with a resolution of nanoseconds. A `minDuration` of 0 or missing means no minimum. `/usr/bin/time -v` measures the wall time in hundredths of a second, so a run shorter than 10 ms is reported as 0 seconds, and a `minDuration` below 0.01 seconds only rejects the runs measured as 0. Wall time varies some milliseconds between runs of the same program (scheduling, load of other submissions), so minimums of a few tenths of a second give stable verdicts. Test cases do not start after the `maxTotalDuration` of the submission (30 seconds if missing): the run ends with a `timeout` status and says how many test cases were not run. The running test case is cut at that time, and the container is killed if the submission lasts 20 seconds more (`DEADLINE_GRACE`).

Requests to `/run` larger than 16 MiB, or with invalid JSON, types, languages, or sizes, are rejected with a 4xx status. The backend has no authentication: it must not be reachable from the Internet, only from the frontend.

Containers have the label `vygoj=engine`. If a backend process is killed during a submission, its container may remain; remove it with:

[source,bash]
----
$ docker rm -f $(docker ps -aq --filter label=vygoj=engine)
----

[[run_log]]
== Run log

The backend logs every submission it receives in `/run`, with its verdict (`src/run_log.py`), in the same format as the activity log of the frontend (see `frontend/readme.adoc`), which statistical software reads as a table. It is written in `data/log/`, next to the logs of gunicorn:

----
data/log/
  runs-2026-11.tsv      # one row per submission of November 2026 (UTC); the first row names the columns
  code/<hash>.c         # code of each judged submission, named by the SHA-256 of its language and code
----

The frontend sends a `context` object with each submission, besides the `problem` and the `solution`: the id of the run in its activity log, the user, their role and address, the course, the material and its type, and the commit of the course repo. The backend does not use it to judge, it only logs it; a submission without context is judged and logged with empty cells. A context that is not an object of up to 32 fields with names of up to 64 characters, and values that are texts of up to 256 characters, numbers, booleans, or null, is rejected with HTTP 400.

[cols="1,4",options="header"]
|===
| Column | Meaning
| `time` | Date and time in UTC, ISO 8601 with milliseconds, e.g. `2026-11-08T14:03:12.345+00:00`
| `id` | The `run` of the context: the `id` of the run event in the activity log of the frontend, which joins both logs. A random id if the frontend did not send it
| `frontend` | Network address of the frontend that sent the submission
| `event` | `run` if the submission was judged, or `run_invalid` if it was rejected with HTTP 400
| `user`, `role`, `address`, `course`, `material`, `type` | Fields of the context
| `data` | JSON object. For `run`: `language`; `code`, the hash of its file; `duration`, seconds the submission took; `status` and `passed` (test cases) of the result; and `tests`, with the `status`, `wallTime`, `cpuTime`, `memory` (bytes), `threadCount`, and `exitCode` of each test case, omitted when they are 0. For `run_invalid`: `reason`. Other fields of the context (e.g. `commit`) go in `context`
|===

The log keeps no test cases or outputs. Cells never contain tabs or new lines, texts are truncated to 256 characters, and the files are readable only by the user that runs the backend. Several gunicorn workers write the same log safely (see `vyg.TsvLog` in `common/vyg/tsv_log.py`, shared with the frontend).


[[development]]
== Development

Check the Python code of `src/` and of the shared `vyg` package with Pylint. The first run installs Pylint in the virtual environment. The configuration, shared with the frontend, is in `common/pylintrc`:

[source,bash]
----
$ make lint
----
