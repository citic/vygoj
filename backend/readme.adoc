= VygOJ backend
:experimental:
:nofooter:
:source-highlighter: pygments
:sectnums:
:toc:
:xrefstyle: short

The backend is the code execution service of VygOJ. The frontend sends it the solution of a student with the test cases of the problem; the backend compiles the solution, runs it with each test case, and answers the verdicts: whether the outputs are the expected ones, how long each test case took, how much memory it used, and, for concurrent programs, how many threads it created. Students never reach the backend: only the frontend does.

Each solution runs in a disposable container of Docker, the *engine*, which isolates it from the computer and from the other solutions, and is destroyed after the run. This document explains how to install, configure, run, stop, and update the backend. Developers find how it works in link:design/readme.adoc[design/readme.adoc].


[[languages]]
== Programming languages

The backend runs solutions in these languages, with these compilers:

[cols="1,2,3",options="header"]
|===
| Language | Default main file | Compiler

| C | `solution.c` | GCC, standard C17 with GNU extensions
| C++ | `solution.cpp` | G++, standard C++20 with GNU extensions
| Java | `Solution.java` | The default JDK of Debian trixie. The main class must be the public class `Solution`
| Python | `solution.py` | Python 3 of Debian trixie
| Alecci | `solution.ale` | https://pypi.org/project/alecci/[alecci] 1.x, a pseudo-language for teaching concurrent programming
|===

A solution may have up to 32 files, of 256 KiB together: the main file of its language, which the student may rename keeping its extension (e.g. `tree.c`, or `Tree.java` with the public class `Tree`), and others that the student adds with the extensions of that language (`.c` and `.h` in C, `.cpp` and `.hpp` in C++, `.java` in Java, `.py` in Python). Alecci solutions have one file.

Problems may also check C and C++ solutions with sanitizers (`asan`, `tsan`, `ubsan`), valgrind (`memcheck`, `helgrind`), and `cpplint` (`lint`).


[[install]]
== Installation

The backend runs on Linux (see the distributions in the link:../readme.adoc#packages[root readme]), and on macOS for development. In production, install it with a user of its own in the `docker` group, e.g. `vygoj-backend`, in its own copy of VygOJ (see the link:../readme.adoc[root readme]).

[[install_docker]]
=== Docker

The backend needs Docker. If the computer does not have it, install it with the package manager of the distribution, as the link:../readme.adoc#packages[dependencies] of the root readme show. For example, in Debian and Ubuntu:

[source,sh]
----
sudo apt install docker.io
----

The user that runs the backend must be in the `docker` group. In production it is the user of the backend (see the link:../readme.adoc#users[users of the programs]). To develop with your own user, add it to the group, and log in again so the change applies:

[source,sh]
----
sudo usermod -aG docker $USER
----

[[install_image]]
=== Engine image

Build the image of the containers, `vygoj-engine`, which has the compilers and tools of the supported languages. It takes some minutes:

[source,sh]
----
cd backend/engine
make image
----

[[install_backend]]
=== Backend

Install the Python dependencies of the backend in a virtual environment (`.venv`):

[source,sh]
----
cd backend
make install
----


[[configuration]]
== Configuration

The backend has no configuration file. These values are in its `Makefile`, and can be changed in the command line, e.g. `make service HOST=10.0.0.4`:

[cols="1,1,3",options="header"]
|===
| Setting | Default | Meaning

| `HOST` | `0.0.0.0` | Address where the backend listens. `0.0.0.0` accepts connections in every address of the computer
| `PORT` | `9090` | Port where the backend listens
| `WORKERS` | `8` | Solutions that the backend runs at the same time. Each one may use up to 2 CPUs and 512 MiB of memory
|===

The backend has no passwords: whoever reaches its port can run code in it. It must not be reachable from the Internet, only from the frontend. Let it listen on a private address, and let the firewall accept only the frontend (see the configuration in several computers of the link:../readme.adoc#configuration[root readme]).

The frontend finds its backends in the `BACKENDS` setting of `frontend/config/config.py`, e.g. `BACKENDS = ['http://10.0.0.4:9090', 'http://10.0.0.5:9090']`.


[[running]]
== Running the server

Docker must be running before the backend starts. Without it, the backend says that Docker is required and stops.

In production, run the backend as a systemd service, which starts it when the computer boots and starts it again if it fails (see the link:../readme.adoc#running[root readme]):

[source,sh]
----
sudo cp ~vygoj-backend/vygoj/backend/vygoj-backend.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vygoj-backend
----

Other ways to run it, from the `backend/` folder:

[source,sh]
----
make            # debug server, for development; Ctrl+C stops it
make release    # without debug messages; Ctrl+C stops it
make server     # in the background, keeps running after logging out
----

Check that the backend answers, from its computer or from the frontend:

[source,sh]
----
curl http://localhost:9090/status
----

The service writes its log in the journal of systemd (`journalctl -u vygoj-backend -f`), and `make server` in the `data/` folder (`access.log` and `error.log`). The backend also logs every solution that it runs in `data/log/`, without the test cases or outputs.


[[stopping]]
== Stopping the server

[source,sh]
----
sudo systemctl stop vygoj-backend     # the service
make stop                             # a server started with make server
----

Before stopping a backend in production, remove it from `BACKENDS` of the frontend and restart the frontend, so no runs are sent to it.

If the backend stops during a run, its container may remain. The service removes them when it stops; otherwise, remove them with:

[source,sh]
----
docker rm -f $(docker ps -aq --filter label=vygoj=engine)
----


[[updating]]
== Updating the server

Get the new code, install the dependencies again, and rebuild the image, all with `make update`, then restart the service:

[source,sh]
----
sudo -iu vygoj-backend make -C vygoj/backend update
sudo systemctl restart vygoj-backend
----

Rebuild the image regularly (e.g. once a month), even without new versions of VygOJ, to receive the security updates of Debian:

[source,sh]
----
cd backend/engine
make rebuild
----

The solutions that are running finish with the old image, and the new ones use the new image, so the backend does not need to stop. The old image is removed.


[[engine]]
== Trying the engine

Professors and developers may open a container of the engine and try its compilers and tools by hand. The container is removed when its shell ends:

[source,sh]
----
cd backend/engine
make run
----


[[uninstall]]
== Uninstalling

Remove the image and its containers with `make remove-image` in `backend/engine/` (stop the backend first), and the virtual environment with `make clean` in `backend/`. Docker is removed with the package manager of the distribution, e.g. `sudo apt remove docker.io` in Debian, if no other program uses it.
