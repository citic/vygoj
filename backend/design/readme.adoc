= VygOJ backend design
:experimental:
:nofooter:
:source-highlighter: pygments

:toc:

This document explains how the backend judges a submission, and why. It is written for developers. The installation and operation of the backend are in link:../readme.adoc[its readme], and the processes of VygOJ in the link:../../design/readme.adoc[root design].

The backend is a Flask web service (`src/main.py`) with two endpoints: `GET /status`, with its health, its version and commit (see link:../../design/readme.adoc#versions[versions]), and the count of running jobs, and `POST /run`, which receives a problem and a solution and answers an `ExecutionResult` (`common/vyg/`). `src/execution.py` drives each submission (`Execution`), and `src/run_log.py` logs it. Gunicorn serves it with 8 single-threaded workers, which bound the submissions that run at the same time.

`Execution.execute()` runs the steps in order, and any step that finds a verdict raises `FailedSolution`, which stops the run with that verdict: a static check fails, the language is not one of the problem, the code does not compile, or a test case fails. Other exceptions are logged with their details, and the user only gets a generic message (`internal error`), because the details may reveal paths or the configuration of the host. The container is removed in `finally`, also on errors, so containers do not pile up.

`/run` answers an `ExecutionResult` in compact JSON. A test case marked `custom` was written by the user (e.g. the input of a problem without test cases): it runs as any other, but its outputs are not compared and its standard error is not a failure. Each test case reports its wall time, its CPU time (all threads added up), its maximum memory, measured with `/usr/bin/time -v`, and, when the problem asks for a minimum of threads, the secondary threads it created, counted with `gdb` in another run with the same arguments and input. The time limits and the thread counts are checked for each test case on its own. Outputs are compared complete, but the answer carries only the first `maxOutputSize` bytes of the problem (at most 1 MiB) of the standard output and error of each visible test case, and of the compiler output, followed by `(truncated)`. Hidden test cases carry no output, and the numbers that the solution chooses are hidden too: their exit code is 0 or 1 (it was not 0), their threads, memory, and times are 0 (also in the logs and in `maxWallTime`), and the numbers of their messages are `N`; their status still tells a timeout. The input of each test case is copied to the container just before it runs, so the solution cannot read the inputs of the following ones, and hidden test cases run after the visible ones, so the outputs of a visible test case cannot have what a hidden one read, e.g. its input saved in a file by the solution. For the same reason the linter runs right after compiling, before any test case could leave files that it reads (such as `CPPLINT.cfg` or Python modules of the user), and a solution that it rejects is a `compilerError` whatever its test cases did. The results are answered in the order of the test cases: if some test case ran, the ones that did not, because the total time was over, are `pending` with the message `Not run`. The status of the submission is the one of the last test case that failed in the order they ran, so a failed hidden test case wins over a failed visible one.


[[languages]]
== Programming languages

The backend runs solutions in C, C++, Java, Python, and Alecci (`LANGUAGE_DEFAULTS` in `src/execution.py`). Each language has a fixed source file name, its compiler command and compile time limit, and the command that runs the solution. Python is interpreted, so its "compiler" only checks the syntax, and students get their syntax errors as compiler errors before any test case runs:

[cols="1,2,3,1,2"]
|===
| Language | Source file | Compiler | Compile limit | Run

| C | `solution.c` | `gcc -g -Wall -Wextra -std=gnu17 -pthread` | 2 s | `./solution`
| C++ | `solution.cpp` | `g++ -g -Wall -Wextra -std=gnu++20 -pthread` | 2 s | `./solution`
| Java | `Solution.java` | `javac -g -encoding UTF-8 -Xlint:all -d .` (the default JDK of Debian trixie) | 10 s | `java -ea -cp . Solution`
| Python | `solution.py` | `python3 -m py_compile` (Python 3 of Debian trixie) | 2 s | `python3 solution.py`
| Alecci | `solution.ale` | `alecci --no-tsan` (https://pypi.org/project/alecci/[alecci] 1.x, which links with clang) | 5 s | `./solution`
|===

Java requires a public class to be in a file of its name, so the main class of a Java solution must be the public class `Solution`, as in the default code of the frontend. Java solutions run with assertions enabled (`-ea`). The sanitizers (`asan`, `tsan`, `ubsan`) and valgrind (`memcheck`, `helgrind`) work only on native executables, so they are ignored for Java and Python, as is `lint`, which runs `cpplint` on C and C++ only. `gdb` counts the threads of C, C++, and Python solutions (the threads of Python are threads of the operating system), but not of Java, whose virtual machine creates threads of its own.

Alecci is a pseudo-language for teaching concurrent programming. Its compiler translates the solution to LLVM IR and links it with clang into a native executable, so `gdb` counts its threads, and valgrind works on it. The compiler enables ThreadSanitizer by default, but TSan creates a thread of its own, which `gdb` would count, so the backend passes `--no-tsan` unless the problem asks for `tsan`; `asan` becomes `--use-asan`, and `ubsan` and `lint` are ignored. The compiler writes status lines on every compilation (`Compiling with thread sanitizer support`, `Compilation successful! ...`), which the backend removes from the compiler output, and it exits with status 0 even when clang fails, so the backend checks that the executable exists after compiling (for every language that creates a file). The engine installs it from PyPI in a virtual environment (`/opt/alecci`), with its major version fixed (`alecci~=1.8`); rebuild the image to get its fixes.

To support a new language, install its compiler in the image (`engine/Dockerfile`), add it to `LANGUAGE_DEFAULTS`, and add its default code to the frontend (see the link:../../frontend/design/readme.adoc#default_code[frontend design]).


[[engine]]
== Engine image

The engine is the Docker image `vygoj-engine` (`engine/Dockerfile`), from which the backend creates a container per submission. It is based on a fixed release of Debian (`debian:trixie`), whose packages receive security updates, and has the compilers and analysis tools of the supported languages (`build-essential`, `clang`, `default-jdk-headless`, `python3`, `cpplint`, `checkstyle`, `valgrind`, `gdb`, `linux-perf`, `time`), the Alecci compiler in `/opt/alecci`, and the unprivileged user `student` (uid 1000, `STUDENT_UID` in `src/execution.py`), whose home `/home/student` is the working directory.

The name `vygoj-engine` is a contract between `engine/Makefile` (`IMAGE`) and `IMAGE` in `src/execution.py`: change both together. The image has the label `vygoj=engine`, so `make rebuild` removes only the old images of VygOJ. The rules of the images (`image`, `rebuild`, `remove-image`) are shared with the language server in `common/docker.mk`: `rebuild` downloads the last version of the base image and installs the packages again (`--pull --no-cache`), and the name moves to the new image when it is built, so running solutions end in the old image and new ones use the new image, without stopping the backend.


[[isolation]]
== Isolation

The backend runs code written by untrusted users, so each submission runs in a disposable container created with restrictions (see `_create_container()` in `src/execution.py`):

[mermaid]
....
include::container.mmd[]
....

* Unprivileged `student` user, all Linux capabilities dropped, `no-new-privileges`, and the default seccomp profile of Docker. The container never runs in privileged mode.
* No network.
* Limits of memory (512 MiB without swap), processes and threads (512), CPUs (2), file size (64 MiB), open files (4096), and a 64 MiB `/tmp` kept in memory.
* Every command has a time limit, its output is truncated to 1 MiB per stream, and student processes left in background are killed after each test case. The whole submission is killed after 100 seconds.
* Command line arguments of test cases are split as a shell would, but they are never interpreted by a shell. Commands run with `docker exec` and a list of arguments, never a shell string, and the solution and the input of each test case (just before it runs) are copied with `put_archive` to fixed file names.

`put_archive` cannot write into a tmpfs, so `/home/student` stays on the writable layer of the container, bounded by the limit of file size.

Requests to `/run` larger than 16 MiB, or with invalid JSON, types, languages, or sizes, or with points of a test case out of the range from -1000000 to 1000000 (`MAX_POINTS` of `vyg`), are rejected with a 4xx status. The backend has no authentication: it must not be reachable from the Internet, only from the frontend.

Containers have the label `vygoj=engine`. If a backend process is killed during a submission, its container may remain; the systemd unit removes them when the service stops (`ExecStopPost`), and they can be removed by hand with:

[source,bash]
----
docker rm -f $(docker ps -aq --filter label=vygoj=engine)
----

Without Docker, `src/execution.py` logs that Docker is required and exits with status 4 when it is imported, which stops gunicorn instead of restarting its workers forever. `make server` and `make service` check it before starting gunicorn (`docker-check`).


[[limits]]
== Time limits

The frontend sends the effective limits in the problem; the backend only clamps them to its own ranges (`MAX_DURATION`, 30 seconds per test case, and `MAX_TOTAL_DURATION`, 120 seconds per submission, in `src/execution.py`), which must contain the ranges of its frontends. Each test case runs at most its `maxDuration` (2 seconds if missing), enforced by `timeout` with a resolution of nanoseconds. A `minDuration` of 0 or missing means no minimum.

`/usr/bin/time -v` measures the wall time in hundredths of a second, so a run shorter than 10 ms is reported as 0 seconds, and a `minDuration` below 0.01 seconds only rejects the runs measured as 0. Wall time varies some milliseconds between runs of the same program (scheduling, load of other submissions), so minimums of a few tenths of a second give stable verdicts.

Test cases do not start after the `maxTotalDuration` of the submission (30 seconds if missing): the run ends with a `timeout` status and says how many test cases were not run. The running test case is cut at that time, and the container is killed if the submission lasts 20 seconds more (`DEADLINE_GRACE`).


[[run_log]]
== Run log

The backend logs every submission it receives in `/run`, with its verdict (`src/run_log.py`), in the same format as the activity log of the frontend (see the link:../../frontend/design/readme.adoc#activity_log[frontend design]), which statistical software reads as a table. It is written in `data/log/`, next to the logs of gunicorn:

----
data/log/
  runs-2026-11.tsv      # one row per submission of November 2026 (UTC); the first row names the columns
  code/<hash>.c         # code of each judged submission, named by the SHA-256 of its language and code
----

The frontend sends a `context` object with each submission, besides the `problem` and the `solution`: the id of the run in its activity log, the user, their roles (separated by spaces) and address, the course, the material and its type, and the commit of the course repo. The backend does not use it to judge, it only logs it; a submission without context is judged and logged with empty cells. A context that is not an object of up to 32 fields with names of up to 64 characters, and values that are texts of up to 256 characters, numbers, booleans, or null, is rejected with HTTP 400.

[cols="1,4",options="header"]
|===
| Column | Meaning
| `time` | Date and time in UTC, ISO 8601 with milliseconds, e.g. `2026-11-08T14:03:12.345+00:00`
| `id` | The `run` of the context: the `id` of the run event in the activity log of the frontend, which joins both logs. A random id if the frontend did not send it
| `frontend` | Network address of the frontend that sent the submission
| `event` | `run` if the submission was judged, or `run_invalid` if it was rejected with HTTP 400
| `user`, `role`, `address`, `course`, `material`, `type` | Fields of the context
| `data` | JSON object. For `run`: `language`; `code`, the hash of its file; `duration`, seconds the submission took; `status` and `passed` (test cases) of the result; and `tests`, with the `status`, `wallTime`, `cpuTime`, `memory` (bytes), `threadCount`, and `exitCode` of each test case, omitted when they are 0. For `run_invalid`: `reason`. Other fields of the context (e.g. `commit`) go in `context`
|===

The log keeps no test cases or outputs. Cells never contain tabs or new lines, texts are truncated to 256 characters, and the files are readable only by the user that runs the backend. Several gunicorn workers write the same log safely (see `vyg.TsvLog` in `common/vyg/tsv_log.py`, shared with the frontend).


[[development]]
== Development

Check the Python code of `src/` and of the shared `vyg` package with Pylint. The first run installs Pylint in the virtual environment. The configuration, shared with the frontend, is in `common/pylintrc`:

[source,bash]
----
make lint
----
