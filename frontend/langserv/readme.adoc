= VygOJ language server
:experimental:
:nofooter:
:source-highlighter: pygments
:sectnums:
:toc:
:xrefstyle: short

The language server gives the code editor of the problem page the suggestions and parameter hints of a professional editor: typing `fge` in C suggests `fgets` with its parameters and documentation, typing `fgets(line,` highlights its parameter `int n`, and choosing a function of a header that the code does not include adds its `#include`. It is optional: without it, the editor only suggests the words already written in the code.

It serves C and C++ (with `clangd`), Python (with `pylsp`), and Java (with `jdtls` of Eclipse). Java gives its first suggestions about 20 seconds after the editor opens, and may suggest some classes newer than the Java version that runs the solutions. Alecci has no language server yet: its editor suggests the keywords of Alecci and the words of the code.

The language server never runs the code of students: it only reads it to suggest. Each open editor gets a container of its own, so the language server needs memory for the editors open at the same time. This document explains how to install, configure, run, stop, and update it. Developers find how it works in link:design/readme.adoc[design/readme.adoc].


[[install]]
== Installation

The language server needs Docker, like the backend (see the link:../../readme.adoc#packages[dependencies] of the root readme to install it). The user that runs it must be in the `docker` group, which gives it the powers of `root`, so use a user of its own, e.g. `vygoj-langserv`, not the one of the frontend (see the link:../../readme.adoc[root readme]). It may run in the computer of the frontend or in another one, which may have a private address (<<several_servers>>).

First, build the image of the containers, `vygoj-lang-srv`, with the language servers and the libraries that solutions include. It takes some minutes:

[source,sh]
----
cd frontend/langserv
make image
----

Second, install the Python dependencies in a virtual environment (`.venv`). It also writes the secret shared with the frontend in `config/config.py`: the one of the frontend if the frontend is in this computer, or a random one:

[source,sh]
----
make install
----


[[configuration]]
== Configuration

The language server loads its default settings from `config/defaults.py`, which explains each one, and replaces them with the ones of `config/config.py`. Do not edit `defaults.py`; write in `config.py` only the settings that change. Two settings are needed:

[source,python]
----
# The same secret as LANG_SERVER_SECRET in frontend/config/config.py
LANG_SERVER_SECRET = '...'
# The address of the site, as users type it in their browsers
ORIGINS = ['https://vygoj.citic.ucr.ac.cr']
----

If the frontend is in another computer, copy its `LANG_SERVER_SECRET` here. Other settings limit the editors open at the same time (`MAX_SESSIONS`, 100), the editors of a user (`MAX_USER_SESSIONS`, 3), and the memory of each one (`CONTAINER_MEMORY`, 512 MiB).

Then tell the frontend where the language server is, in `LANG_SERVERS` of `frontend/config/config.py`, as browsers reach it, and restart the frontend. In development, the default value is the address of the language server in the same computer:

[source,python]
----
LANG_SERVERS = ['ws://localhost:7070']
----

The address and port where the language server listens are `HOST` and `PORT` in its `Makefile` (`0.0.0.0` and `7070`), and can be changed in the command line, e.g. `make service HOST=127.0.0.1`.

[[reverse_proxy]]
=== Behind the reverse proxy of the frontend

In production, browsers connect to the language server through the reverse proxy of the frontend, Apache or nginx, with HTTPS (see the link:../readme.adoc#reverse_proxy[reverse proxy of the frontend]). In Apache, whose commands already enable the module of WebSockets (`proxy_wstunnel`), add this line before the `ProxyPass /` of the frontend, because Apache uses the first one that matches:

[source,config]
----
ProxyPass /lang-srv/ ws://127.0.0.1:7070/
----

In nginx, add this block to the `server` of port 443, next to the `location /` of the frontend. nginx closes connections without messages after 60 seconds by default, so the block waits longer than the language server, which closes the editors without messages after 15 minutes (`IDLE_TIMEOUT`):

[source,config]
----
location /lang-srv/ {
    proxy_pass http://127.0.0.1:7070/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 20m;
    proxy_send_timeout 20m;
}
----

Then the frontend uses `LANG_SERVERS = ['wss://vygoj.citic.ucr.ac.cr/lang-srv/']`, and the language server, in the same computer, may listen only on `127.0.0.1`. In another computer, write its private address instead of `127.0.0.1` (see the configuration in several computers of the link:../../readme.adoc#configuration[root readme]).

[[several_servers]]
=== Several language servers

When the editors open at the same time do not fit in one computer, run language servers in several computers, each one with the same `LANG_SERVER_SECRET` and `ORIGINS`, and list them in `LANG_SERVERS` of the frontend. Each user always gets the same server. If a server stops, its users get no suggestions until it starts again or leaves the list.

Browsers only reach the frontend, so the other computers may have private addresses: the reverse proxy of the frontend passes a path to each one. Each server listens on its private address, and a firewall lets only the computer of the frontend connect to its port. The connections between the reverse proxy and the servers are not encrypted, so they must go through a private network. In Apache:

[source,config]
----
ProxyPass /lang-srv/1/ ws://10.0.0.11:7070/
ProxyPass /lang-srv/2/ ws://10.0.0.12:7070/
----

In nginx, one `location` block for each server, like the one above, with its path and its address: `location /lang-srv/1/` with `proxy_pass http://10.0.0.11:7070/;`, and so on.

The frontend lists the paths:

[source,python]
----
LANG_SERVERS = ['wss://vygoj.citic.ucr.ac.cr/lang-srv/1/', 'wss://vygoj.citic.ucr.ac.cr/lang-srv/2/']
----


[[running]]
== Running the server

In production, run it as a systemd service, which starts it when the computer boots and starts it again if it fails (see the link:../../readme.adoc#running[root readme]):

[source,sh]
----
sudo cp ~vygoj-langserv/vygoj/frontend/langserv/vygoj-langserv.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vygoj-langserv
----

Other ways to run it, from the `frontend/langserv/` folder:

[source,sh]
----
make          # debug server, for development; Ctrl+C stops it
make server   # in the background, logs and pid file in data/
----

The service writes its log in the journal of systemd (`journalctl -u vygoj-langserv -f`).


[[stopping]]
== Stopping the server

[source,sh]
----
sudo systemctl stop vygoj-langserv    # the service
make stop                             # a server started with make server
----

Students keep editing and running their code; they only lose the suggestions. The service removes the containers of the editors when it stops. Otherwise, remove them with:

[source,sh]
----
docker rm -f $(docker ps -aq --filter label=vygoj=lang-srv)
----


[[updating]]
== Updating the server

Get the new code, install the dependencies again, and rebuild the image, all with `make update`, then restart the service:

[source,sh]
----
sudo -iu vygoj-langserv make -C vygoj/frontend/langserv update
sudo systemctl restart vygoj-langserv
----

Rebuild the image regularly (e.g. once a month) with `make rebuild`, to receive the security updates of Debian. Open editors keep the old image, and new ones get the new image.
