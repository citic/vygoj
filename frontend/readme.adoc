= VygOJ frontend
:experimental:
:nofooter:
:source-highlighter: pygments

:stem: latexmath

The web application component allows professors to create courses and students to attend them. It is compound of two parts:

. The app's frontend is an XHTML/CSS/JS application for running on web browsers.
. The app's backend is a Python application using Flask framework.

You need command-line access to the machine where the app will be installed. The following instructions assume a Unix-like environment.



[[setup]]
== Setup

Run `make install` to create the Python virtual environment and install the required dependencies. You can run a local instance of the frontend for development (`make`), local production (`make run`), or production server (`make server`):

[source,sh]
----
make install
make server
----

Now you can access the frontend at http://localhost:8080 or any other port you configured. The backend should be running and accessible from the frontend in order to run code. Read the user manual in `docs/` folder for creating users, courses, and assignments.

[[linters]]
=== Linters

The Python code in `src/` and in the shared `vyg` package (`common/vyg/`) is checked with Pylint (configured in `common/pylintrc`, shared with the backend). The client code in `static/` is checked with ESLint (AirBnB style guide, configured in `.eslintrc.cjs`) and Stylelint (standard configuration with the class names of the project: one snake_case class per component, configured in `.stylelintrc.json`). Run `make lint` in the `frontend/` folder: the first time it installs Pylint in the virtual environment and the others with npm, then runs the three, and fails if any finds problems. Make stops at the first linter that fails; `make -k lint` runs the rest anyway.

[source,sh]
----
make lint
----

`make pylint` runs only Pylint, and `make lint-static` only ESLint and Stylelint. To run these two separately, or to fix automatically what is safe to fix:

[source,sh]
----
npx eslint static/js
npx eslint --fix static/js
npx stylelint 'static/css/**/*.css'
npx stylelint --fix 'static/css/**/*.css'
----

`npm run lint` and `npm run stylelint` run the first and third commands. ESLint needs the folder to check: `npx eslint` without arguments checks no files and reports no problems.


[[reverse_proxy]]
== Reverse proxy configuration

You may want to run the VygOJ frontend on port 80 (HTTP) and 443 (HTTPS). However, for security reasons, the Flask server should run on a port greater than 1024. A reverse proxy using Apache or Nginx helps to reach both goals. The following instructions are for Apache2.

Run the frontend in a non-privileged port, for example, 8080. Use a process manager such as Gunicorn, that keeps the frontend running even if it crashes. For example:

[source,sh]
----
gunicorn --bind 127.0.0.1:8080 main:app
----

// TODO(jhc): find real command
// gunicorn -w 4 --bind 0.0.0.0:8080 main:app --daemon

Install Apache and Let's Encrypt. Enable the Apache proxy modules using root privileges:

[source,sh]
----
sudo a2enmod proxy
sudo a2enmod proxy_http
sudo a2enmod headers
sudo a2enmod ssl
----

Create a new Apache configuration file, for example, `/etc/apache2/sites-available/vygoj.conf`, and add the following content. Change `vygoj.citic.ucr.ac.cr` to your domain name, and the paths to your SSL certificate files.


[source,config]
----
<VirtualHost *:80>
    ServerName vygoj.citic.ucr.ac.cr
    ServerAlias www.vygoj.citic.ucr.ac.cr

    # Redirect all HTTP traffic to HTTPS
    Redirect permanent / https://vygoj.citic.ucr.ac.cr/
</VirtualHost>

<VirtualHost *:443>
    ServerName vygoj.citic.ucr.ac.cr
    ServerAlias www.vygoj.citic.ucr.ac.cr

    ProxyPreserveHost On
    ProxyPass / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    # Recommended headers for proxying
    RequestHeader set X-Forwarded-Proto "https"
    RequestHeader set X-Forwarded-Port "443"

    # SSL configuration for your domain
    SSLEngine On
    SSLCertificateFile /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/cert.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/privkey.pem

    # Error and Access logging
    ErrorLog ${APACHE_LOG_DIR}/vygoj-error.log
    CustomLog ${APACHE_LOG_DIR}/vygoj-access.log combined
</VirtualHost>
----

Apache sends the address of each client in the `X-Forwarded-For` header. Set `TRUSTED_PROXIES = 1` in `config/config.py`, so the frontend uses that address for the login limits (<<login_limits>>) and the logs. Otherwise, every request seems to come from `127.0.0.1`, and the failed logins of all the users count as the ones of a single address. Keep it `0` if clients connect to the frontend directly, because they could fake that header.

Enable the new configuration, test it, and restart Apache:

[source,sh]
----
sudo a2ensite vygoj
sudo apachectl configtest
sudo systemctl restart apache2
----


[[security]]
== Security

The frontend is exposed to the Internet and receives untrusted data from students and from course repositories. This section explains the controls it applies, so they are kept when the code changes.

[[secret_key]]
=== Session key

Flask signs the session cookie with `SECRET_KEY` of `config/config.py`. The session stores the logged user and their role, so anyone who knows the key can forge a session of any user, including administrators. The frontend refuses to start if the key is missing (it is empty in `config/defaults.py`), is the public example key of an old configuration file, or has fewer than 32 characters. Generate a random key with:

[source,sh]
----
python3 -c 'import secrets; print(secrets.token_hex(32))'
----

Changing the key logs out all users, because their cookies are no longer valid.

[[csrf]]
=== Cross-site request forgery (CSRF)

Every POST request must carry the CSRF token of the session (Flask-WTF `CSRFProtect`), otherwise it is rejected with HTTP 400:

* Forms send it in their hidden `csrf_token` field (`form.hidden_tag()`).
* The problem page writes it in the `data-csrf-token` attribute of `<main id="problem">`, and `problem.js` sends it in the `X-CSRFToken` header. The problem endpoint also requires a JSON body, which HTML forms of other sites cannot send.
* Tokens last as long as the session (`WTF_CSRF_TIME_LIMIT = None`), because students keep a problem page open for hours.
* Logout changes the session, so `/logout` only accepts POST.

The session cookie is also `Secure`, `HttpOnly`, and `SameSite=Lax`.

[[csp]]
=== Content security policy (CSP)

Problem statements come from course repositories and are shown as HTML. Talisman (the `flask-talisman` package) sends a `Content-Security-Policy` header (`cdn` in `src/main.py`) where scripts may only come from files of this site and from the CDNs the pages use (jsDelivr, cdnjs, esm.sh). Inline scripts, event handler attributes (`onclick`), and `javascript:` URLs do not run, so templates must not have them: put behavior in `static/js/`. Styles allow `'unsafe-inline'` because Monaco and MathJax inject `<style>` elements. The policy also forbids plugins (`object-src`), foreign `<base>` elements, forms that post to other sites, and being embedded by other sites.

Talisman also redirects HTTP to HTTPS (except in debug mode) and sends `Strict-Transport-Security`, `Referrer-Policy: strict-origin` (other sites only see that links came from VygOJ, not from which page), and `Permissions-Policy`, which disables the camera, the microphone, the geolocation, and the Topics API of advertising. `set_headers()` in `src/main.py` adds the `Cross-Origin-*` headers that Talisman does not send. Configure in Talisman the headers it sends, because it sets them after `set_headers()` and would replace them.

[[course_repos]]
=== Course repositories

Problem folders and files are read only if their real path, after resolving symbolic links, is inside the folder of the course repository. Otherwise, a `folder` such as `../..` in `vygoj.json`, or a symbolic link committed to a repo, could show any readable file of the server (e.g. `config.py`) as a statement or a test case. Skipped files are logged as warnings. Files larger than 16 MiB are skipped too. Asciidoc statements are converted in the `safe` mode of `asciidoctor`.

A test case has the keys `args` (command line arguments, split as a shell would), `stdin`, `stdout`, and `stderr` (expected outputs), the same names of the outputs of its result. In the `tests` folder of a problem they are the files `args<n>.txt`, `input<n>.txt`, `output<n>.txt`, and `error<n>.txt`. Test cases marked `"hidden": true` are sent to the browser without them.

[[statements]]
=== Problem statements

Statements are converted to HTML on the server (Asciidoctor resolves `include::` directives there) and then sanitized with https://pypi.org/project/nh3/[nh3] by `sanitize_html()` in `src/sanitize.py`, once per problem load. The same function is meant for other HTML written by course authors, such as the content pages of the future. The sanitizer keeps an allow list of tags, attributes, and CSS properties, which covers what Asciidoctor, Markdown, and hand-written HTML produce. It removes:

* Scripts, styles, forms, plugins, inline SVG and MathML (with their contents), event handler attributes (`onclick`...), and the `<head>` and `<title>` of statements written as whole HTML documents.
* Frames and videos of other sites (see <<videos>>).
* URLs with schemes other than `http`, `https`, and `mailto` (e.g. `javascript:` and `data:`), and URLs such as `//host/path`.
* CSS properties that could place the statement over the page (e.g. `position`). Allowed ones are listed in `STYLE_PROPERTIES`.

The ids of a statement get the prefix `content_` (and its `#section` links too), so they cannot replace the elements of the page that JavaScript looks for, such as `run_button` or `language`.

Formulas (`stem`) are kept as text, and MathJax typesets them in the browser. To show an SVG image, use `image::` (an `<img>` element), because inline SVG is removed.

[[videos]]
=== Videos

Statements may play video files of their folder with `video::media/demo.mp4[]` (a `<video>` element), with subtitles in `vtt` files if wanted. Videos of video sites (`video::id[youtube]`, `video::id[vimeo]`, or any `<iframe>`) and video files of other sites are removed for now, and the CSP of the pages forbids frames (`frame-src 'none'`) and media of other sites (`media-src 'self'`). Supporting them requires an allow list of sites and a sandbox for their players, and pages that embed them cannot send `Cross-Origin-Embedder-Policy: require-corp`, because video sites do not opt in to it.

The sanitizer sets `controls` and `preload="metadata"` on every video, and removes `autoplay`. Posters (`poster=`) must be images of the folder too.

[[problem_files]]
=== Files of problem folders

Statements refer to images and videos of their folder with relative URLs, such as `img/diagram.svg`. The sanitizer rewrites them to `/problem/<course>/<problem>/files/img/diagram.svg`, served by `ProblemController.get_file()`. This route only serves files that:

* have an extension of an image (`avif`, `gif`, `jpeg`, `jpg`, `png`, `svg`, `webp`), a video (`mp4`, `ogv`, `webm`), or subtitles (`vtt`), listed in `FILE_TYPES` in `src/problems.py`. Test cases, solutions, `vygoj.json`, and any other file of the problem folder are never served. Files included in a statement with `include::` are not served either; their contents are already in the statement.
* are inside the folder of the problem, after resolving symbolic links, not in other problems of the course.

Files are streamed, so videos have no size limit, and range requests let students jump to any second. They are served with their own strict CSP (`FILE_CSP` in `src/main.py`), with `sandbox`, because an SVG may contain scripts that would run if a student opened its URL. Images from other sites stay blocked by the CSP of the pages (`img-src 'self' data:`), so students do not reveal their addresses to third parties.

[[login_limits]]
=== Login attempts

Failed logins are stored in the `login_attempts` table (`LoginAttempt` in `src/users.py`), so all the gunicorn workers share their counts. During 15 minutes (`LOGIN_WINDOW`), the frontend accepts:

* 5 failed logins of a user from the same address (`MAX_FAILURES_PER_USER`), which stops a student from guessing the password of a classmate.
* 30 failed logins from the same address for any users (`MAX_FAILURES_PER_ADDRESS`), which stops robots that try many users. It is larger because a whole laboratory may share a public address.

Then, logins from that address are rejected, without checking the password, until the oldest failures are older than 15 minutes. Usernames that do not exist count too, so the limits do not reveal which users exist. A successful login forgets the failures of that user from that address. There is no limit per username alone, otherwise anybody could lock the account of a classmate by typing wrong passwords before an exam. Failed and rejected logins are logged as `login_failed` and `login_blocked`.

The limits depend on the address of the client, so set `TRUSTED_PROXIES` behind a reverse proxy (<<reverse_proxy>>).

[[run_limits]]
=== Code runs

Only logged users may run code (see <<input_limits>>). Their runs are stored in the `runs` table (`Run` in `src/runs.py`), so all the gunicorn workers apply the same limits. When a user presses Run:

. If the code and language are the same as the last run of that user in that problem, and the problem is judged the same way, the stored result of that run is answered, without running the code again. It covers students who reload the page or press Run again, also from another browser, and robots that repeat a submission. Submissions are compared by a SHA-256 hash (`Run.hash_code()`), which takes less than a millisecond for the largest submissions (1 MiB). The hash includes the problem as it is sent to the backend (its test cases, effective limits, and other fields that change verdicts), so results are not reused after the professor changes them and the server reloads the course repo, or after the administrator changes the limits. Changes in the statement do not count.
. Otherwise, the run is rejected with HTTP 429, a message, and a `Retry-After` header if:
** the previous run of the user has not finished yet (one run at a time). A run without end 15 seconds (`STALE_RUN_GRACE`) after the longest wait for a backend (110 seconds with the example limits) does not count, so a server restart cannot block users.
** the previous run started less than 5 seconds ago (`MIN_RUN_INTERVAL`).
** the user started 120 runs in the last hour (`MAX_RUNS_PER_WINDOW`). A student who runs the code every 30 seconds stays below it.

The checks and the new run are stored while the row of the user is locked (`SELECT ... FOR UPDATE`), so two requests sent at the same time cannot both pass. Only the result of the last run of each problem is kept, if it is smaller than 1 MiB, and runs older than one day are deleted. Repeated and rejected runs are logged as `run_repeated` and `run_rejected`.

The frontend sends the backend a compact JSON object (`run_solution()` in `src/problems.py`) with only two parts: the solution, and the fields of the problem that judge it (`BACKEND_FIELDS`: the test cases, the languages, the limits, and other fields that change verdicts), not the statement or the initial code. It answers the browser the JSON of the backend as it came, parsed only to store the grade. Texts travel as JSON strings, so code and output in any language arrive intact.

The administrator sets the limits of the runs in `config.py` (their defaults and explanation are in `config/defaults.py`). Each limit has an absolute range (`ABS_MIN_*`, `ABS_MAX_*`) and a default (`DEF_*`), which may be a number or a dictionary with a number for each language. Professors may choose a value in `vygoj.json`, for the problem or for a test case; values out of the range are clamped, and a missing value or 0 means the default. `src/limits.py` computes the effective values and sends them in the problem. The frontend does not start with invalid limits.

[cols="2,3,1,1",options="header"]
|===
| Field | Meaning | Range | Default
| `minDuration`, `maxDuration` | Wall time in seconds of each test case (`*_RUN_DURATION`). A `minDuration` of 0 means no minimum. The wall time is measured in hundredths of a second (see `backend/readme.adoc`) | 0 to 10 | 0 and 2 (C, C++) to 6 (Python)
| `maxTotalDuration` | Seconds of the whole submission. Test cases that do not fit are not run (`*_TOTAL_DURATION`) | 0 to 60 | 30
| `maxOutputSize` | Bytes of the standard output and error of each visible test case, and of the compiler output, shown to students, followed by `(truncated)` (`*_OUTPUT_SIZE`) | 0 to 10 KiB | 10 KiB
|===

Outputs are compared complete, and hidden test cases send no output, so students cannot see what their inputs made the program write.

The browser never waits forever, and it always gets an answer before giving up. The frontend waits for the backend the `maxTotalDuration` of the submission plus 30 seconds (`BACKEND_GRACE` in `src/limits.py`), and the backend answers before. The problem page gets in `data-run-timeout` how long the browser waits for a run: the longest wait for a backend plus 10 seconds (105 seconds with the example limits). Other requests are aborted after 30 seconds. `site.js` checks the connection with the judge (`/status`) every minute, and every 10 seconds while it is lost. While the browser is offline, the status check fails, or a run cannot reach the judge, the problem page shows an error and disables the Run button; it enables it again when the connection is restored.

[[administrators]]
=== Administrators

Administrators are created in the server with `make admin` (`src/manage_users.py admin`), never from the web application, so only who can log in the server can create them. The command asks the username and a password of at least 12 characters. If the user exists, it resets its password, makes it administrator, and forgets its failed logins, so it also recovers a forgotten password. While the users table is empty, the frontend writes a warning in its log that suggests `make admin`.

[[input_limits]]
=== Requests and errors

* Request bodies are limited to 1 MiB (`MAX_CONTENT_LENGTH`, can be overridden in `config.py`).
* Problem actions are validated: only `fetch_problem` and `run`, and only the languages enabled for the problem.
* Only logged users may run code. Anonymous visitors may read problems and their test cases, but the problem page shows them a "Log in to run" link instead of the Run button, and the server answers their `run` requests with HTTP 401, also when a robot or a command sends them.
* Errors are answered with generic messages such as `{"error": "the judge is not available"}`; their details (backend addresses, host paths) go to the server log only.
* The request log (`data/vygoj.tsv`) stores the body of JSON requests only, never the bodies of forms, which carry passwords.
* Login takes the same time whether the user exists or not, and starts a new session.
* After logging in, users go to the page in the `next` parameter of the login page (e.g. `/user?next=/problem/CI0112/hello`, used by the "Log in to run" link). `safe_next_url()` in `src/users.py` accepts only paths of this site, otherwise anybody could write a link to the login of VygOJ that takes students to a fake site after logging in (open redirect).
