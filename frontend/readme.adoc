= VygOJ frontend
:experimental:
:nofooter:
:source-highlighter: pygments
:sectnums:
:toc:
:xrefstyle: short

The frontend is the web application of VygOJ, the only program that users reach with their browsers. Professors publish their courses in it, students enroll in courses and solve their problems, and administrators manage the users. It sends the solutions of students to a backend to run them, and it shows the verdicts.

This document explains how to install, configure, run, stop, and update the frontend, and what it offers to administrators, professors, and students. Developers find how it works in link:design/readme.adoc[design/readme.adoc].


[[install]]
== Installation

The frontend runs on Linux (see the distributions and their packages in the link:../readme.adoc#packages[root readme]), and on macOS for development. In production, install it with a user of its own that is not in the `docker` group, e.g. `vygoj-frontend`, in its own copy of VygOJ (see the link:../readme.adoc[root readme]). It needs the OpenSSH client, which it uses to copy the repositories of professors and students, and Asciidoctor, which converts the problem statements to HTML (see the link:../readme.adoc#packages[dependencies]).

[[install_dependencies]]
=== Dependencies

Install the Python dependencies in a virtual environment (`.venv`). It also creates the configuration file `config/config.py` with the random secrets that the frontend needs to start:

[source,sh]
----
cd frontend
make install
----

[[install_database]]
=== Database

The frontend stores the users, their progress, and the courses with their sections and students in a PostgreSQL database. To have the database in the same computer, install and start PostgreSQL with the commands of _Database_ of the distribution, in the link:../readme.adoc#packages[dependencies of the root readme]. Then create a database for the user of the frontend. In macOS, only run `createdb vygoj`, because the user that installed PostgreSQL is already its administrator:

[source,sh]
----
sudo -u postgres createuser $USER
sudo -u postgres createdb -O $USER vygoj
----

The frontend creates its tables when it starts, and updates them after an update of VygOJ. To have the database in another computer, see the configuration in several computers of the link:../readme.adoc#configuration[root readme].

[[install_admin]]
=== First administrator

Create the first administrator in the server. The command asks the username, the full name, and the password (at least 12 characters, not shown while typed):

[source,sh]
----
make admin
----

Then the administrator logs in the web application and adds the other users (<<users>>). Run the command again to reset the password of an administrator who forgot it; the username can be given as `make admin ADMIN=name`. Only who can log in the server can create administrators this way.


[[configuration]]
== Configuration

The frontend loads its default settings from `config/defaults.py`, which explains each one, and replaces them with the ones of `config/config.py`. Write in `config.py` only the settings that change; do not edit `defaults.py`, which is part of VygOJ. `config.py` has secrets and passwords, so only the user of the frontend may read it. Restart the frontend after changing it. The main settings are:

[cols="1,3",options="header"]
|===
| Setting | Meaning

| `DATA_FOLDER` | Folder where the frontend keeps the repositories of the users and the activity log, e.g. `/home/vygoj-frontend/vygdata`. It must exist
| `SQLALCHEMY_DATABASE_URI` | Address of the database. `postgresql+psycopg:///vygoj` is the database `vygoj` of the same computer, with the user of the frontend; `postgresql+psycopg://user:password@10.0.0.2/vygoj` is one in another computer
| `BACKENDS` | Addresses of the backends, e.g. `['http://10.0.0.4:9090', 'http://10.0.0.5:9090']`. Each run goes to one of them at random
| `LANG_SERVERS` | Addresses of the language servers, as browsers reach them (see link:langserv/readme.adoc[the language server]). `[]` turns them off, and the editor only suggests the words of the code
| `SITE_URL` | Address of the site as users type it, e.g. `https://vygoj.citic.ucr.ac.cr`. Needed for single sign-on behind a reverse proxy
| `TRUSTED_PROXIES` | `1` behind a reverse proxy (<<reverse_proxy>>), `0` otherwise
| `REPO_ORIGIN_HOSTS` | Git hosts where users may keep their repositories, e.g. GitHub and GitLab. Add the Git host of the institution if it has one
| `SSO_CLIENT_SECRETS` | Secrets of the single sign-on providers (<<sso>>)
| `SECTION_CURRENCIES` | Currencies that professors choose for the cost of their sections (<<professor_repos>>), e.g. `['CRC', 'USD']`, the first one by default
| `SECRET_KEY`, `LANG_SERVER_SECRET` | Secrets written by `make install`. Changing `SECRET_KEY` logs out all users
|===

[[limits]]
The settings `*_RUN_DURATION`, `*_TOTAL_DURATION`, and `*_OUTPUT_SIZE` limit the runs of solutions. Each limit has a range that professors may choose from in their problems, and a default:

[cols="2,3,1,1",options="header"]
|===
| Field of a problem | Meaning | Range | Default

| `minDuration`, `maxDuration` | Seconds that each test case may take, at least and at most. A minimum of 0 means no minimum | 0 to 10 | 0, and 2 (C, C++) to 6 (Python)
| `maxTotalDuration` | Seconds of the whole run. Test cases that do not fit are not run | 0 to 60 | 30
| `maxOutputSize` | Bytes of output of each test case shown to students | 0 to 10 KiB | 10 KiB
|===


[[running]]
== Running the server

In production, run the frontend as a systemd service, which starts it when the computer boots and starts it again if it fails (see the link:../readme.adoc#running[root readme]):

[source,sh]
----
sudo cp ~vygoj-frontend/vygoj/frontend/vygoj-frontend.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vygoj-frontend
----

Other ways to run it, from the `frontend/` folder:

[source,sh]
----
make            # debug server, for development; Ctrl+C stops it
make release    # without debug messages; Ctrl+C stops it
make server     # in the background, keeps running after logging out
----

The frontend listens on port 8080: open http://localhost:8080 in a browser. The backend must be running to run code. The service writes its log in the journal of systemd (`journalctl -u vygoj-frontend -f`), and `make server` in the `data/` folder.


[[stopping]]
== Stopping the server

[source,sh]
----
sudo systemctl stop vygoj-frontend    # the service
make stop                             # a server started with make server
----

While the frontend is stopped, the site is not available. Users stay logged in after it starts again.


[[updating]]
== Updating the server

Get the new code and install the dependencies again, both with `make update`, then restart the service. The frontend updates its database tables when it starts:

[source,sh]
----
sudo -iu vygoj-frontend make -C vygoj/frontend update
sudo systemctl restart vygoj-frontend
----

Back up the database (`pg_dump vygoj`) and the `DATA_FOLDER` regularly, and before an update.


[[reverse_proxy]]
== Reverse proxy

Users reach the site with HTTPS, on the standard ports 80 and 443, but the frontend should run on a port greater than 1024 for security reasons. A web server in front of it, a reverse proxy, reaches both goals: it receives the connections of the browsers, encrypts them with the certificate of the site, and passes them to the frontend and to the language server. These instructions are for Apache and for nginx; choose one of them, and install it with the dependencies of the frontend (see the link:../readme.adoc#packages[root readme]).

Run the frontend in port 8080, as a systemd service (<<running>>), listening only on `127.0.0.1`, because the reverse proxy is in the same computer. `sudo systemctl edit vygoj-frontend` opens an editor: write these three lines in the empty space at the top, above the comment `### Edits below this comment will be discarded`, and do not change the service file shown below that comment, because the editor discards those lines. The empty `ExecStart=` removes the command of the service file, because a service has only one, and the next line gives the new one:

[source,config]
----
[Service]
ExecStart=
ExecStart=/usr/bin/make service HOST=127.0.0.1
----

Save, and restart the frontend with `sudo systemctl restart vygoj-frontend`.

In Fedora and RHEL, SELinux does not let the reverse proxy connect to other programs until `httpd_can_network_connect` is enabled, for Apache and for nginx:

[source,sh]
----
sudo setsebool -P httpd_can_network_connect 1
----

[[certificate]]
=== Certificate

`certbot` gets the certificate of the site from Let's Encrypt, free, and renews it before it expires. Get it before configuring the site, because the configuration names its files. Use the option of your reverse proxy, `--apache` or `--nginx`, and change `vygoj.citic.ucr.ac.cr` to your domain name:

[source,sh]
----
sudo certbot certonly --apache -d vygoj.citic.ucr.ac.cr -d www.vygoj.citic.ucr.ac.cr
----

The files of the certificate are left in `/etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/`. Debian and Ubuntu renew it automatically. In Fedora and RHEL, enable its timer with `sudo systemctl enable --now certbot-renew.timer`; in Arch, create a timer as the https://wiki.archlinux.org/title/Certbot[Arch wiki] shows.

[[apache]]
=== Apache

Enable the modules of Apache for the proxy, the headers, HTTPS, and WebSockets (for the language server):

Debian, Ubuntu::
+
[source,sh]
----
sudo a2enmod proxy proxy_http proxy_wstunnel headers ssl
----

Fedora, RHEL::
The package of Apache loads those modules by default.

Arch::
Remove the `#` at the beginning of the lines of `/etc/httpd/conf/httpd.conf` that load the modules `mod_proxy.so`, `mod_proxy_http.so`, `mod_proxy_wstunnel.so`, `mod_headers.so`, `mod_ssl.so`, and `mod_socache_shmcb.so`, and add the lines `Listen 443` and `Include conf/extra/vygoj.conf` at its end.

The configuration file of the site and the commands to enable it depend on the distribution:

[cols="1,2,2",options="header"]
|===
| Distribution | Configuration file of the site | Enable it, test it, and restart Apache

| Debian, Ubuntu
| `/etc/apache2/sites-available/vygoj.conf`
| `sudo a2ensite vygoj`, `sudo apachectl configtest`, `sudo systemctl restart apache2`

| Fedora, RHEL
| `/etc/httpd/conf.d/vygoj.conf`
| `sudo apachectl configtest`, `sudo systemctl restart httpd`

| Arch
| `/etc/httpd/conf/extra/vygoj.conf`
| `sudo apachectl configtest`, `sudo systemctl restart httpd`
|===

Create the configuration file of the site with the following content. Change `vygoj.citic.ucr.ac.cr` to your domain name. In Fedora, RHEL, and Arch, write `logs/` instead of `${APACHE_LOG_DIR}/`, which only Debian defines.

[source,config]
----
<VirtualHost *:80>
    ServerName vygoj.citic.ucr.ac.cr
    ServerAlias www.vygoj.citic.ucr.ac.cr

    # Redirect all HTTP traffic to HTTPS
    Redirect permanent / https://vygoj.citic.ucr.ac.cr/
</VirtualHost>

<VirtualHost *:443>
    ServerName vygoj.citic.ucr.ac.cr
    ServerAlias www.vygoj.citic.ucr.ac.cr

    # The language server goes here, before ProxyPass /, see langserv/readme.adoc
    ProxyPreserveHost On
    ProxyPass / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    # Recommended headers for proxying
    RequestHeader set X-Forwarded-Proto "https"
    RequestHeader set X-Forwarded-Port "443"

    # Certificate of the site, with its chain, and its private key
    SSLEngine On
    SSLCertificateFile /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/privkey.pem

    # Error and Access logging
    ErrorLog ${APACHE_LOG_DIR}/vygoj-error.log
    CustomLog ${APACHE_LOG_DIR}/vygoj-access.log combined
</VirtualHost>
----

The language server is reached through the same Apache, with a `ProxyPass` line before `ProxyPass /`, because Apache uses the first one that matches (see link:langserv/readme.adoc#reverse_proxy[the language server]). Enable the configuration, test it, and restart Apache with the commands of the table above. In Debian and Ubuntu:

[source,sh]
----
sudo a2ensite vygoj
sudo apachectl configtest
sudo systemctl restart apache2
----

[[nginx]]
=== nginx

The configuration file of the site and the commands to enable it depend on the distribution:

[cols="1,2,2",options="header"]
|===
| Distribution | Configuration file of the site | Enable it, test it, and reload nginx

| Debian, Ubuntu
| `/etc/nginx/sites-available/vygoj`
| `sudo ln -s /etc/nginx/sites-available/vygoj /etc/nginx/sites-enabled/`, `sudo nginx -t`, `sudo systemctl reload nginx`

| Fedora, RHEL
| `/etc/nginx/conf.d/vygoj.conf`
| `sudo nginx -t`, `sudo systemctl reload nginx`

| Arch
| `/etc/nginx/conf.d/vygoj.conf`, and add the line `include conf.d/*.conf;` inside the `http` block of `/etc/nginx/nginx.conf`
| `sudo nginx -t`, `sudo systemctl reload nginx`
|===

Create the configuration file of the site with the following content. Change `vygoj.citic.ucr.ac.cr` to your domain name:

[source,config]
----
# Redirect all HTTP traffic to HTTPS
server {
    listen 80;
    listen [::]:80;
    server_name vygoj.citic.ucr.ac.cr www.vygoj.citic.ucr.ac.cr;
    return 301 https://vygoj.citic.ucr.ac.cr$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name vygoj.citic.ucr.ac.cr www.vygoj.citic.ucr.ac.cr;

    # Certificate of the site, with its chain, and its private key
    ssl_certificate /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/vygoj.citic.ucr.ac.cr/privkey.pem;

    # The largest request that the frontend accepts (MAX_CONTENT_LENGTH)
    client_max_body_size 1m;

    # The language server goes here, see langserv/readme.adoc
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-Port 443;
    }

    access_log /var/log/nginx/vygoj-access.log;
    error_log /var/log/nginx/vygoj-error.log;
}
----

The language server is reached through the same nginx, with a `location /langserv/` block (see link:langserv/readme.adoc#reverse_proxy[the language server]). Enable the configuration, test it, and reload nginx with the commands of the table above. In Debian and Ubuntu:

[source,sh]
----
sudo ln -s /etc/nginx/sites-available/vygoj /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
----

[[proxy_settings]]
=== Settings of the frontend

Set two settings in `config/config.py`, and restart the frontend:

* `SITE_URL = 'https://vygoj.citic.ucr.ac.cr'`, if users log in with single sign-on (<<sso>>): the frontend receives `http://` requests from the reverse proxy, but the addresses registered in the providers are `https://`.
* `TRUSTED_PROXIES = 1`, so the frontend knows the address of each user, which the reverse proxy sends. It limits the failed logins by address (<<user_limits>>). Without it, every request seems to come from `127.0.0.1`, and the failed logins of all the users count as the ones of a single address. Keep it `0` if users connect to the frontend directly, because they could fake their address.


[[administration]]
== Administration

[[users]]
=== Users

Administrators manage the users in the users page, the _Users_ link of the home page. Each user has one or more roles: student, assistant, professor, director, and administrator, e.g. a professor who is also a student of a course of another professor. Users log in with their username and password, or with the account of their institution (<<sso>>).

The list of users can be filtered by any words, e.g. a name, and by column, e.g. `role:professor`. Clicking the name of a column sorts the users by it, and its pin keeps it as the first sort key. Each user has these actions:

[cols="1,4",options="header"]
|===
| Action | Effect

| Edit (pencil) | Change the full name, email, roles, and status of the user
| Suspend (pause) | The user cannot log in, and is logged out at once. Their data is kept, and _Activate_ lets them log in again
| Delete (red X) | Removes the user and all their data: progress, repositories, courses, and enrollments. Their activity stays in the log. It cannot be undone: only backups recover them
|===

Administrators cannot remove their own administrator role nor suspend themselves, so there is always an administrator.

The _Import users_ section adds many users at once from a CSV or TSV file in UTF-8, such as the one that a spreadsheet saves, of up to 200 users. Its first line names the columns: `username` and `email` are required, and `fullname`, `password`, `role`, `status`, `language`, and `font` are optional. The page has examples of both formats. After the import, a table tells which users were imported, which already existed, and which were rejected and why. A file can be imported again: the users that already exist are skipped. A file cannot create administrators.

[[sso]]
=== Single sign-on (SSO)

Users may log in with the account of their institution instead of a password of VygOJ, through an OpenID Connect (OIDC) provider, such as the Keycloak of the Universidad de Costa Rica. Administrators manage the providers in the users page: the _+ Add_ button opens the form of a new provider, and each provider of the table has _Edit_ and _Delete_ buttons. The form asks:

[cols="1,3",options="header"]
|===
| Field | Meaning

| Alias | Short name chosen in VygOJ (not the client ID) for URLs and for `SSO_CLIENT_SECRETS`, e.g. `ucr`. It cannot change, because it is part of the callback URL registered in the provider
| Name | Text of the login button, e.g. _Universidad de Costa Rica_
| Status | _Disabled_: nobody can log in with it. _Testing_: it is not shown in the login page, but its login URL (`/login/sso/<alias>`) works, for a controlled test in production. _Active_: the login page shows its button above the password form
| Discovery URL or issuer | e.g. `https://sso.ucr.ac.cr/realms/UCR`; `/.well-known/openid-configuration` is added if missing. Only `https://`, or `http://` for a provider in the same computer
| Client ID | Given by the team of the provider
| Scopes | `openid profile email` by default
| Email claim | Claim with the email of the user, `email` by default (some providers send `mail`)
| Trust emails | Accept the emails of the provider even if the ID token does not have `email_verified: true`, e.g. an institution that assigns the emails itself
| Create accounts | Users without an account in VygOJ get one at their first login. Otherwise only existing users may log in with the provider
| Professor claim and values | Optional rule for the role of new users: if the claim (e.g. `groups`, or `realm_access.roles` for nested claims) has one of the values (separated by commas), the user is a professor, otherwise a student
|===

To connect a provider:

. Add it with status _Disabled_ and save it. The form shows the redirect URI (callback) to register in the provider: `<SITE_URL>/login/sso/<alias>/callback`. Set `SITE_URL` in `config.py` to the public address of the site (e.g. `https://vygoj.ucr.ac.cr`), because behind a reverse proxy the frontend sees `http://` addresses, and the redirect URI must match exactly.
. Ask the team of the provider for a client, with that redirect URI, the scopes and claims needed (the email, the name, and the claim of the professor rule if any), and no Web Origins: tokens are exchanged in the server. Logout only ends the session of VygOJ, so no post logout redirect URI is needed. Ask for separate clients for tests and production.
. Write the client secret in `config.py`, by the alias of the provider, and restart the frontend. Secrets are credentials, so they are never stored in the database nor shown in the web forms. The form only tells whether the secret is configured. A provider without secret is used as a public client, protected by PKCE only:
+
[source,python]
----
SSO_CLIENT_SECRETS = {'ucr': 'the secret given by the SSO team'}
----
. Fill the Client ID, set the status to _Testing_, and log in from the login URL that the form shows. When it works, set it to _Active_.

At their first login with a provider, users with that email in VygOJ are linked to their account, and may log in with their password or with the provider from then on. Other users get a new account if the provider creates accounts, or are asked to contact their professor. Administrators never get linked by email: an administrator logs in with their password until they link their account.

[[activity_log]]
=== Activity log

The frontend logs the activity of the users to know how the judge is used, follow the progress of students, recover their submissions, and do research: logins, visits to pages, runs of solutions, and the changes that administrators and professors make. It never logs passwords. It keeps the log in the `log/` folder of `DATA_FOLDER`, a file per month that spreadsheets and statistical software read as a table.

Administrators download two zip files from the _Administration_ panel of the home page:

* *Activity log*: the files of the log, and tables ready to analyze in `analysis/`: `events.tsv` (every event), `runs.tsv` (a row per run of a solution, with its verdict), `tests.tsv` (a row per test case of each run), and `materials.tsv` (the sections and problems of the courses, to group the events).
* *Submissions*: the code that each user sent to each problem, with the statement and test cases that judged it, to run the submissions again. It may be much larger than the log.

For example, to load the tables in R or Python and join the runs with their test cases:

[source,r]
----
runs <- read.delim("analysis/runs.tsv", quote = "", colClasses = "character")
tests <- read.delim("analysis/tests.tsv", quote = "", colClasses = "character")
verdicts <- merge(runs, tests, by.x = "id", by.y = "run")
----

[source,python]
----
import pandas
runs = pandas.read_csv('analysis/runs.tsv', sep='\t', quoting=3, dtype=str)
tests = pandas.read_csv('analysis/tests.tsv', sep='\t', quoting=3, dtype=str)
verdicts = runs.merge(tests, left_on='id', right_on='run')
----

The same archives are written in the command line of the server:

[source,sh]
----
cd src
../.venv/bin/python manage.py log vygoj-log.zip
../.venv/bin/python manage.py submissions vygoj-submissions.zip
----

The columns of the log and the fields of each event are described in the link:design/readme.adoc#activity_log[design document].


[[courses]]
== Courses and repositories

[[professor_repos]]
=== Courses of professors

Professors write their courses in git repositories of their own, with their editor and a Git host such as GitHub or GitLab, and VygOJ reads them. A repository may have one course or several, listed in a configuration file of its root: `vygoj.json`, `vygoj.yaml`, `info.json`, or `info.yaml`.

In the _Repositories_ section of the home page, professors add the SSH address of each repository (e.g. `git@github.com:ann/courses.git`), and give read access to the SSH key that the section shows. _Clone_ copies the repository to VygOJ, and _Pull_ brings its changes later. The messages of the section tell the courses found, or what is wrong.

Professors offer a course in sections (groups): _Offer_ opens a form with the duration of the section (intensive, monthly, two months, quarter, four months, semester, annual, or indefinite) and its weeks (the longest of the duration is suggested, e.g. 20 for a semester, which may be changed to 16), its year and term (I, II, III), optional start, end, and archive dates, its institution, campus, and numbers (001 to 999; several numbers separated by spaces, such as `003 005 006`, offer several sections at once), its modality of study (regular, tutoring, challenge exam, adaptive, or self-paced), how students enroll (by themselves, with an optional password, or by the professor), and its cost and currency. Required fields have a red asterisk, and _Offer_ is enabled when they are filled. Students enroll from the start date; the end date is the end of the lessons (without it, the section is available forever), and the archive date closes the enrollment. The form estimates the end and archive dates from the start date and the weeks, and remembers its values in the browser for the next section. A course may be offered in many sections. Each section shows the version of the course of the last _Pull_ when it was offered: later changes reach its students only when the professor presses _Update_ in the section. _Edit_ opens the form of the section again. Enrollment by the professor (a list of emails or a CSV file) and payments are not available yet.

The home page shows four lists of courses, each section of a course in a row below its card:

[cols="1,4",options="header"]
|===
| List | Courses

| My prepared courses | Only for professors: the courses of their repositories, which only they see, to review them. _Offer_ offers a course in a new section
| My taught sections | Only for professors: the sections that they offered, with their students, and the buttons _Update_ and _Edit_
| My enrolled courses | The courses where the user is enrolled, with their section and progress
| Available courses | The sections where the user may enroll by themselves, from their start date until their end date. A user enrolls in one section of each course
|===

Only the professor of a course, its students, and administrators enter it. Students see the version of their section, and the professor and administrators the last _Pull_.

[[problems]]
=== Problems

Each problem is a folder of the course repository with its statement, the initial code of each language, and its test cases:

* The statement is a file `.html`, `.adoc` (Asciidoc), or `.md` (Markdown). It may have formulas, images, and videos of the folder of the problem. Scripts, and frames and videos of other sites, such as YouTube, are removed.
* The initial code is in its `initial/` or `given/` folder. Without it, students start from the default code of the language.
* The test cases are in its `tests/` folder: `input001.txt` with the standard input of the first test case, `output001.txt` with its expected output, `error001.txt` with its expected standard error, and `args001.txt` with its command line arguments.

The folder may have a configuration file too, with the same names as the one of the root of the repository. For example, in YAML:

[source,yaml]
----
title: Dining philosophers
languages: [c, cpp]         # by extension or name, in any case
maxDuration: 2.0            # seconds of each test case
tools: [helgrind, lint]     # a list or a text: "helgrind lint"
tests:
  default: {points: 2}      # every test case of the tests folder
  004: {points: 5, hidden: true}   # the one of tests/input004.txt
----

Hidden test cases are not shown to students. The limits of time and output are explained in <<limits>>, and every field in the link:design/readme.adoc#problem_config[design document]. The problem page shows the professor, and nobody else, what the judge skipped of the configuration file.

[[student_repos]]
=== Solutions of students

Every user has a student repository, a git repository in VygOJ with the history of their solutions. Each run of a solution saves a new version of the code, unless it did not change. The code editor of the problem page has a slider with the versions of the solution, to see or recover an older one.

Students may also write test cases of their own, e.g. a case that the professor did not include. In a problem with test cases, the _+_ button above the tabs adds one, with its arguments, input, and an optional expected output, and _−_ deletes the selected one; a run has up to 100 test cases, the ones of the professor included. Each run saves them in the student repository, with the solution, and runs them after the ones of the professor: their tabs have a dashed border, and they give no points nor count in the passed test cases. Their output is compared only if they have an expected output.

In the _Repositories_ section of the home page, students download a zip with their last solutions, or a zip with the whole history, and may push their repository to a Git host of their own (_Origin_ and _Push_), after giving write access to the SSH key that the section shows. Zips take some time to be ready, and are kept for 24 hours.


[[user_limits]]
== Limits for users

To protect the users and the judge, the frontend limits:

* *Failed logins*: after 5 failed logins of a user, or 30 of any users from the same address, in 15 minutes, the frontend rejects the logins of that address until 15 minutes pass. Usernames are never locked, so nobody can lock the account of a classmate.
* *Runs of solutions*: only logged users run code, one run at a time, at least 5 seconds apart, and at most 120 runs per hour. Running the same code again answers the same result without running it.

Users choose the language of the interface, the color scheme, and the font in their preferences. VygOJ is in English and Spanish.
